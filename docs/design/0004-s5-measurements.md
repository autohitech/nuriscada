# 설계 0004. S5 측정 기록 (진행 중)

> 상태: **진행 중.** [O] CI에 세 OS 부하 측정과 의존성 목록(SBOM) 생성을 추가했다. [U] 기준 하드웨어(D-4) 검증과 72시간 안정성 시험은 남아 있다. CI 실행 결과는 아래 기록과 구분한다.

- 기계: Apple M5 Pro, 15코어, 24 GB (기준 하드웨어 후보 4코어·8 GB보다 훨씬 넉넉하다). 릴리스 빌드. 같은 프로세스에서 시뮬레이터, 스캐너, 서버, 웹소켓 클라이언트를 모두 돌렸다.
- 도구: `cargo run --release -p nuriscada-bench -- --tags 10000 --clients 50 --devices 10 --change-pct 10 --duration-s 60`.

## 1차 결과: 불합격 (프레임마다 방송)

태그 1만 개, 클라이언트 50, 주기 100 ms, 변화율 10%: 지터 p99 32 ms(한도 20 ms), 놓친 주기 459회, CPU 831%, 프레임 2300만 개(15.8 GiB), 스냅샷 재전송 7788회. 스캔만 돌리면(클라이언트 0) p99 3.7 ms, CPU 9%여서 병목은 웹소켓 방송이었다.

## 개선

변경을 주기마다 한 묶음으로 모아 한 번만 부호화해 모든 클라이언트가 공유하고(순번으로 스냅샷과 일관성 유지), 태그는 인덱스로 가리키는 작은 항목으로 보내며, 알람 기록도 묶어서 보낸다. 웹 클라이언트와 설계 0003의 프레임 형식을 이에 맞췄다(`tags`, `alarms`).

## 개선 후 결과 (30초, 클라이언트 50, 1만 태그)

| 장치 | 변화율 | p99 지터 | 놓친 주기 | CPU | 비고 |
|---|---|---|---|---|---|
| 10 | 10% | 3.3 ms | 0 | 13% | 합격 |
| 1 | 10% | 3.4 ms | 0 | 10% | 합격 |
| 10 | 50% | 3.4 ms | 0 | 18% | 합격 |
| 10 | 100% | 3.8 ms | 0 | 22% | 합격 |
| 10 | 0% | 2.2 ms | 0 | 9% | 합격 |

60초 실행: p99 3.9 ms, 놓친 주기 0, CPU 11%. RSS는 88 → 약 345 MiB로 올랐다가 변화율과 무관하게 같은 값이라 클라이언트 50개의 스냅샷 버퍼 때문으로 보이며 누수 여부는 72시간 시험으로 확인해야 한다.

## 미완료·한계
- 기준 하드웨어에서는 측정하지 않았다. CI의 공유 실행기는 기준 하드웨어를 대신하지 않는다.
- 브라우저에서 1만 태그 화면을 열어 값 갱신과 필터 동작은 확인했지만 렌더링 CPU는 측정하지 않았다.
- 같은 프로세스 안의 시험이라 실제 네트워크 지연과 클라이언트 CPU는 반영되지 않았다.
- 실제 MODBUS 장치로 시험하지 않았다. 72시간 연속 운전도 하지 않았다.

## 이어서 추가한 자동 검증 (2026-10-18)

- [O] `.github/workflows/ci.yml`에 Ubuntu·Windows·macOS 부하 작업을 추가했다. 릴리스 빌드로 태그 10,000개·클라이언트 50개·장치 10개·100 ms·변화율 10%를 60초 실행한다. `--check`가 실패하면 작업도 실패하고 `load.json`은 실패 때도 아티팩트로 보관한다. 지터·놓친 주기 기준은 완화하지 않았다.
- [O] Rust는 `cargo-cyclonedx 0.5.9`로 모든 대상 플랫폼의 의존성을 포함한 CycloneDX 1.5 JSON을 크레이트별로 만든다. 웹은 `npm sbom --package-lock-only --sbom-format cyclonedx`로 빌드 의존성을 포함한다. CI 아티팩트 `sbom-cyclonedx`로 보관한다. 배포물 동봉과 서드파티 고지 생성은 별도 과제다.
- [O] 위 두 SBOM 생성 명령을 로컬에서 실행했고 Rust 8개와 웹 1개의 JSON을 읽어 CycloneDX 형식과 구성 요소 목록을 확인했다. SBOM은 의존성 목록이며 라이선스·취약점 검사를 대신하지 않는다.
- [O] Rust 전체 시험, 서식·Clippy 검사, 웹 타입·접근성 검사, 웹 시험 13개, 웹 빌드, 웹 라이선스 검사(62개)가 통과했다.
- [O] 같은 개발 기계에서 60초 재측정: 지터 p99 2.469 ms, 최댓값 3.090 ms, 놓친 주기 0, 요청 실패 0, 클라이언트 50/50, 장치당 최소 스캔 601회로 `--check` 합격. CPU 평균 10.5%, RSS 시작 62 MiB·끝/최대 347 MiB였다. 이 짧은 측정으로 누수 여부는 판단하지 않는다.
- [O] Orca 브라우저로 알람 100개 표시 제한·나머지 건수, 장치 10개 연결 요약, 검색 후 단일 태그 값의 연속 갱신을 다시 확인했다. 같은 개발 기계의 브라우저 동반 180초 실행도 놓친 주기·요청 실패 0회였다. 렌더링 CPU는 별도 측정하지 않았다.

## 첫 CI 결과와 스냅샷 처리 개선

[O] 커밋 `c885465`의 [CI 실행](https://github.com/autohitech/nuriscada/actions/runs/39090266881)에서 세 OS Rust 시험·정적 검사, 웹, 의존성 검사, SBOM은 모두 통과했다. 부하 측정은 아래처럼 모두 실패했다. 모든 경우 클라이언트는 50개 연결했다.

| OS | p99 지터 | 최대 지터 | 놓친 주기 | 요청 실패 |
|---|---|---|---|---|
| Ubuntu | 1.950 ms | 872.885 ms | 88 | 0 |
| macOS | 31.533 ms | 363.846 ms | 80 | 0 |
| Windows | 17.567 ms | 47.962 ms | 120 | 3 |

- [O] 로컬에서도 `TOKIO_WORKER_THREADS=2`로 60초 실행하면 놓친 주기 20회로 실패했다(p99 2.934 ms). 스냅샷 복사·JSON 부호화가 비동기 실행 스레드 안에서 실행되고 있었다.
- [O] 스냅샷 처리를 `spawn_blocking`으로 옮기고 동시 작업 수를 2개로 제한했다. 제한 없는 별도 스레드 처리에서는 RSS가 약 512 MiB까지 올라가므로 동시 작업 수를 제한했다. 구독 → 일관된 스냅샷 → 대기 묶음 순번 검사 순서는 유지한다.
- [O] 제한을 포함한 변경 후 같은 2스레드·60초 부하는 p99 2.503 ms, 최대 2.925 ms, 놓친 주기·요청 실패 0회로 합격했다. CPU 평균 8.2%, RSS 끝/최대 약 259 MiB, 클라이언트 50개, 장치당 최소 스캔 601회였다. Rust 전체 시험·서식·Clippy도 다시 통과했다.
- [I] 비동기 스레드를 점유하는 스냅샷 처리 제거가 작은 스레드 풀의 지연을 줄인 것으로 보인다. CI 실패 전체의 원인을 이것만으로 확정할 수는 없다.
- [U] 변경 후 세 OS CI 재측정, 기준 하드웨어, 72시간 안정성 검증 전에는 S5 완료나 스택 최종 검증으로 판단하지 않는다. 72시간 시험은 아직 시작하지 않았다.
